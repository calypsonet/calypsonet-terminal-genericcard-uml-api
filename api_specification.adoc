== Abstract

This document is the official technical specification of the **{spec-name}** standardised
by the **{organization}** ({short-name}).
It defines, in a language-agnostic way, the interfaces, classes, enumerations, exceptions, structural
relationships and behavioural requirements that any conforming implementation of the {spec-name} MUST satisfy.

The {spec-name} is part of the broader CNA *Terminal API* family. It exposes the minimal contract required to
exchange raw APDUs with a card that has been selected through the *Terminal Reader API*, without prescribing any
specific card application model.

== Introduction

=== Purpose

The {spec-name} defines the contract used by terminal applications that need to exchange raw APDUs with an ISO/IEC
7816-4-compliant card without relying on a card-specific application layer (e.g. Calypso). It complements the
*Terminal Reader API* ([CNA-TR-API]) by providing:

* a card-selection extension that allows additional successful status words to be declared for the *Select
  Application* APDU,
* a minimal transaction manager that prepares APDU commands and processes them as a single batch, returning the
  raw responses to the application.

Conforming implementations MUST guarantee interoperability with reader implementations of the
[CNA-TR-API] specification.

=== Scope

This specification covers:

* the factory used to instantiate the public types of the API,
* the card-selection extension used to enrich the selection scenario for generic cards,
* the transaction manager used to exchange APDUs with the selected card,
* the property holder exposing the API version.

The following topics are *out of scope*:

* the parsing of APDU payloads -- the API exposes raw bytes only,
* the application-level dialogue with specific card products (covered by dedicated specifications),
* the management of secure channels.

=== Conformance

A software product conforms to this specification if and only if:

. it implements every interface and class defined in <<sec_specification>> with the operations and semantics
  prescribed in this document,
. it preserves the structural and behavioural relationships described in <<sec_architecture>>.

Throughout this specification, the key words **MUST**, **MUST NOT**, **SHALL**, **SHALL NOT**, **SHOULD**,
**SHOULD NOT**, **RECOMMENDED**, **MAY** and **OPTIONAL** are to be interpreted as described in **RFC 2119** and
**RFC 8174** when, and only when, they appear in all capitals.

=== Document Conventions

==== Naming

Type names follow `UpperCamelCase`; operation, parameter and enumeration-member names follow `lowerCamelCase`
except for enumeration values which use `UPPER_SNAKE_CASE`. Names defined by this specification are reproduced
exactly as they appear in the reference UML class diagram (<<sec_class_diagram>>).

==== Language-agnostic types

The following symbolic type names are used in operation signatures and are mapped, in each binding, to the closest
equivalent native type. Implementations MUST preserve the semantic intent rather than the syntactic form.

[cols="1,3,3", options="header"]
|===
| Symbolic type   | Description                                                     | Typical bindings
| `string`        | Sequence of characters, UTF-8 encoded by default.                | `String` (Java), `string` (C#), `str` (Rust/Python).
| `boolean`       | Two-state truth value.                                           | `boolean`, `bool`.
| `integer`       | Signed 32-bit integer.                                           | `int`, `Int32`.
| `byte`          | Signed 8-bit value.                                              | `byte`, `i8`.
| `byte array`    | Ordered sequence of octets.                                      | `byte[]`, `[u8]`, `bytes`.
| `list<T>`       | Ordered collection of `T` values, may contain duplicates.        | `List<T>`, `Vec<T>`.
| `void`          | Indicates that an operation returns no value.                    | `void`, `Unit`, `None`.
|===

==== Operation tables

Each operation defined in this document is described by a table of the form:

[cols="1h,4", grid=rows, frame=ends]
|===

| Since       | The version of the specification that introduced the operation.

== Terms, Definitions and Abbreviations

=== Terms and Definitions

[cols="1,4", options="header"]
|===
| Term              | Definition

| APDU              | Application Protocol Data Unit, the message format used between the terminal and the card (ISO/IEC 7816-4).
| Card              | Any physical or virtual smart card that can be presented to a reader.
| Card Application  | Application Dedicated File (DF) selected on a card, identified by its AID, as defined in ISO/IEC 7816-4.
| Generic Card      | Any card whose selection and APDU dialogue can be performed using only the constructs defined by this specification, without recourse to a card-product-specific extension.
| Status Word       | The two-byte trailer of an APDU response indicating the outcome of the command (ISO/IEC 7816-4, §5.1.3).
| SPI               | Service Provider Interface -- a set of interfaces designed to be implemented by an extension module.
|===

=== Abbreviations

[cols="1,4", options="header"]
|===
| Abbreviation | Expansion

| AID  | Application IDentifier
| APDU | Application Protocol Data Unit
| CLA  | CLAss byte of an APDU
| CNA  | Calypso Networks Association
| INS  | INStruction byte of an APDU
| ISO  | International Organization for Standardization
| SW   | Status Word
| UML  | Unified Modelling Language
|===

== Architectural Overview

=== Functional positioning

The {spec-name} extends the *Terminal Reader API* with the minimal contract required to dialogue with a generic
card. The application uses the *Reader API* to select the card, and the *Generic Card API* to exchange APDUs.

App --> TR : uses
GC  --> TR : extends
TR  --> Drv : delegated to
@enduml
....

[[type_GenericCardApiFactory]]
==== GenericCardApiFactory

[cols="1h,4", grid=rows, frame=ends]
|===
| Kind     | Interface
| Package  | `genericcard`
| Since    | 1.0.0
| Purpose  | Factory used by the application to obtain instances of the public types provided by the API.
|===

The `GenericCardApiFactory` is the *only* normative entry point through which the application is allowed to
instantiate the public types of the API. Implementations MUST expose exactly one instance of this factory and MUST
guarantee that every invocation returns a fresh, fully initialised object.

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature   | `createGenericCardSelectionExtension() -> GenericCardSelectionExtension`
| Since       | 1.0.0
| Description | Returns a new, freshly initialised <<type_GenericCardSelectionExtension,`GenericCardSelectionExtension`>>.
| Returns     | A non-`null` <<type_GenericCardSelectionExtension,`GenericCardSelectionExtension`>>.
| Throws      | None.
|===

[cols="1h,4", grid=rows, frame=ends]

| Parameters

[[type_GenericCardSelectionExtension]]
==== GenericCardSelectionExtension

[cols="1h,4", grid=rows, frame=ends]
|===
| Kind     | Interface
| Package  | `genericcard`
| Since    | 1.0.0
| Extends  | `CardSelectionExtension` ([CNA-TR-API])
| Purpose  | Extends the `CardSelectionExtension` interface defined by the *Terminal Reader API* to expose a way to declare additional successful status words for the *Select Application* APDU.
|===

===== Operations

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature   | `addSuccessfulStatusWord(statusWord: integer) -> GenericCardSelectionExtension`
| Since       | 1.0.0
| Description
| Adds a status word to the list of those that MUST be considered successful for the *Select Application* APDU.

  *Note:* the list initially contains the standard successful status word `9000h`.
| Parameters  | `statusWord` -- a positive `integer` lower than or equal to `FFFFh`.
| Returns     | The current instance, to allow fluent composition.
| Throws      | None.
|===

[[type_CardTransactionManager]]
==== CardTransactionManager

[cols="1h,4", grid=rows, frame=ends]
|===
| Kind     | Interface
| Package  | `genericcard`
| Since    | 1.0.0
| Extends  | `CardTransactionManager<CardTransactionManager>` ([CNA-TR-API])
| Purpose  | Provides the basic operations required to prepare and process APDU exchanges with a card.
|===

===== Operations

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature   | `prepareApdu(apduCommand: string) -> CardTransactionManager`
| Since       | 1.0.0
| Description | Prepares an APDU to be transmitted the next time `processCommands(channelControl)` is invoked. The command is supplied as a hexadecimal `string` containing a raw APDU.
| Parameters  | `apduCommand` -- a non-empty hexadecimal `string` containing a raw APDU command.
| Returns     | The current instance, to allow fluent composition.
| Throws      | None.
|===

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature   | `prepareApdu(apduCommand: byte array) -> CardTransactionManager`
| Since       | 1.0.0
| Description | Prepares an APDU to be transmitted the next time `processCommands(channelControl)` is invoked. The command is supplied as a `byte array` containing the raw APDU.
| Parameters  | `apduCommand` -- a non-empty `byte array` containing the raw APDU command.
| Returns     | The current instance, to allow fluent composition.
| Throws      | None.
|===

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature
| `prepareApdu(cla: byte, ins: byte, p1: byte, p2: byte, dataIn: byte array, le: byte) -> CardTransactionManager`
| Since       | 1.0.0
| Description | Prepares an APDU to be transmitted the next time `processCommands(channelControl)` is invoked. The command is supplied through its individual ISO/IEC 7816-4 header bytes, data and expected response length.
| Parameters
| `cla`    -- the class byte. +
  `ins`    -- the instruction byte. +
  `p1`     -- the P1 parameter byte. +
  `p2`     -- the P2 parameter byte. +
  `dataIn` -- the APDU data; `null` if there is no data. +
  `le`     -- the expected output length; `0` if the output length is unspecified; `null` if no output data is expected.
| Returns     | The current instance, to allow fluent composition.
| Throws      | None.
|===

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature   | `getResponsesAsByteArrays() -> list<byte array>`
| Since       | 1.0.0
| Description
| Returns the responses corresponding to the commands executed by the last call to `processCommands(channelControl)`,
  represented as `byte array` values. Each element represents the response of one command, in the same order as the
  commands were prepared.

  This operation MUST NOT alter the internal state of the manager: the list of responses MUST remain available
  until `processCommands(channelControl)` is invoked again, at which point it is replaced by the new set of responses.
| Returns     | A non-`null` `list<byte array>` representing the command responses, in the order in which the commands were sent.
| Throws      | None.
|===

[cols="1h,4", grid=rows, frame=ends]
|===
| Signature   | `getResponsesAsHexStrings() -> list<string>`
| Since       | 1.0.0
| Description
| Returns the responses corresponding to the commands executed by the last call to `processCommands(channelControl)`,
  represented as hexadecimal `string` values. Each element represents the response of one command, in the same order
  as the commands were prepared.

  This operation MUST NOT alter the internal state of the manager: the list of responses MUST remain available
  until `processCommands(channelControl)` is invoked again, at which point it is replaced by the new set of responses.
| Returns     | A non-`null` `list<string>` of hexadecimal strings representing the command responses, in the order in which the commands were sent.
| Throws      | None.
|===

[[sec_behaviours]]
== Behavioural Requirements

. The list of successful status words declared on a `GenericCardSelectionExtension` MUST be cumulative: every call
  to `addSuccessfulStatusWord` adds to the existing set without removing the implicit `9000h` entry.
. The `prepareApdu` overloads MUST be functionally equivalent. The choice between hexadecimal `string`,
  `byte array` and explicit header parameters is purely ergonomic for the calling application.
. `processCommands(channelControl)` (inherited from [CNA-TR-API]) MUST execute the prepared APDUs in the order in
  which they were prepared; the resulting `list` returned by `getResponsesAsByteArrays` and
  `getResponsesAsHexStrings` MUST preserve that order.
. The responses exposed by `getResponsesAsByteArrays` and `getResponsesAsHexStrings` MUST be derived from the
  same underlying response set: invoking either operation MUST return data consistent with the other.
