== Abstract

This document is the official technical specification of the **{spec-name}** standardised
by the **{organization}** ({short-name}).
It defines, in a language-agnostic way, the interfaces, classes, enumerations, exceptions, structural
relationships and behavioural requirements that any conforming implementation of the {spec-name} MUST satisfy.

The {spec-name} is part of the broader CNA *Terminal API* family. It exposes the minimal contract required to
exchange raw APDUs with an ISO/IEC 7816-4 card that has been selected through the *Terminal Reader API*, without
prescribing any specific card application model.

== Introduction

=== Purpose

The {spec-name} defines the contract used by terminal applications that need to exchange raw APDUs with an ISO/IEC
7816-4-compliant card without relying on a card-specific application layer (e.g. Calypso). It complements the
*Terminal Reader API* ([CNA-TR-API]) by providing:

* a card-selection extension that allows additional successful status words to be declared for the *Select
  Application* APDU,
* a minimal transaction manager that prepares APDU commands, attaches an optional command identifier and an
  optional per-command duration bound (relay-attack countermeasure), and processes them as a single batch,
  returning the raw responses to the application.

Conforming implementations MUST guarantee interoperability with reader implementations of the [CNA-TR-API]
specification.

=== Scope

This specification covers:

* the factory used to instantiate the public types of the API,
* the card-selection extension used to enrich the selection scenario for generic cards,
* the transaction manager used to prepare and exchange APDUs with the selected card, including the per-command
  identifier and the per-command duration bound,
* the property holder exposing the API version.

The following topics are *out of scope*:

* the parsing of APDU payloads -- the API exposes raw bytes only,
* the application-level dialogue with specific card products (covered by dedicated specifications),
* the management of secure channels.

=== Conformance

A software product conforms to this specification if and only if:

. it implements every interface and class defined in <<sec_specification>> with the operations and semantics
  prescribed in this document,
. it preserves the structural and behavioural relationships described in <<sec_architecture>>.

Throughout this specification, the key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**,
**MAY** and **OPTIONAL** are to be interpreted as described in **RFC 2119** and **RFC 8174** when, and only when,
they appear in all capitals.

In conformance with RFC 2119, **SHALL** is equivalent to **MUST**; this specification uses **MUST** exclusively in
order to avoid ambiguity.

=== Document Conventions

==== Naming

Type names follow `UpperCamelCase`; operation, parameter and enumeration-member names follow `lowerCamelCase`
except for enumeration values which use `UPPER_SNAKE_CASE`. Names defined by this specification are reproduced
as-is in the UML class diagram (<<sec_class_diagram>>).

==== Language-agnostic types

The following symbolic type names are used in operation signatures and are mapped, in each binding, to the closest
equivalent native type. Implementations MUST preserve the semantic intent rather than the syntactic form.

[cols="1,3,3", options="header"]
|===
| Symbolic type   | Description                                                     | Typical bindings
| `string`        | Sequence of characters, UTF-8 encoded by default.                | `String`, `string`, `str`.
| `boolean`       | Two-state truth value.                                           | `boolean`, `bool`.
| `byte`          | Signed 8-bit value.                                              | `byte`, `i8`.
| `integer`       | Signed 32-bit integer.                                           | `int`, `Int32`.
| `long`          | Signed 64-bit integer.                                           | `long`, `Int64`.
| `byte array`    | Ordered sequence of octets.                                      | `byte[]`, `[u8]`, `bytes`.
| `list<T>`       | Ordered collection of `T` values, may contain duplicates.        | `List<T>`, `Vec<T>`.
| `void`          | Indicates that an operation returns no value.                    | `void`, `Unit`, `None`.
|===

==== Operation tables

Each operation defined in this document is described by a table of the form:

[cols="1h,4", grid=rows, frame=all]
|===
| Signature   | The operation's language-agnostic signature.
| Description | A normative description of the operation's behaviour.
| Parameters  | A description of each input parameter.
| Returns     | A description of the returned value, if any.
| Throws      | A list of exceptional conditions, each mapped to a specific exception type.
|===

==== Operation contracts

To avoid repetition, the following rules apply to every operation table in <<sec_specification>> and are therefore
not restated for each operation:

* *Non-`null` arguments.* Unless explicitly stated otherwise, every input parameter MUST be non-`null`. An
  implementation MUST raise `IllegalArgumentException` if a `null` value is supplied. Operations whose only error
  condition is a `null` argument therefore declare no entry in their *Throws* row.
* *Non-`null` results.* Unless the return type is marked nullable (`T?`) or the *Returns* row states otherwise, an
  operation returns a non-`null` value.
* *Fluent composition.* Builder-style operations return the current instance so that calls can be chained.

== Terms, Definitions and Abbreviations

=== Terms and Definitions

[cols="1,4", options="header"]
|===
| Term              | Definition

| APDU              | Application Protocol Data Unit, the message format used between the terminal and the card.
| Card Reader       | Hardware or software component capable of detecting cards and exchanging data with them.
| Command Identifier| Application-supplied integer attached to a prepared APDU, used to retrieve the corresponding response or to identify the failing command in case of error.

=== API Interfaces

[[type_CardTransactionManager]]
==== Card Transaction Manager

[cols="1h,4", grid=rows, frame=all]
|===
| Kind     | Interface
| Namespace  | `genericcard`
| Since    | 1.0
| Extends  | `IsoCardTransactionManager` ([CNA-TR-API])
| Purpose
| Provides the basic operations required to prepare, identify and process APDU exchanges with an ISO/IEC 7816-4
  card. The stereotype on `IsoCardTransactionManager` grants access to the multi-channel cast
  `asMultichannelCardTransactionManager()` defined by [CNA-TR-API] when the underlying card supports
  multi-channel.
|===

The `CardTransactionManager` uses a *prepare/process* model inherited from [CNA-TR-API]: the application prepares
APDU commands with the `prepareCommand` overloads and processes them through the inherited `processCommands()`
operation. Each prepared command MAY carry an optional *command identifier* (`idCommand`) supplied by the
application, used to retrieve the corresponding response or to identify the failing command in case of error.
Each prepared command MAY also carry an optional *maximum duration* (`maxDuration`, in milliseconds) used by the
implementation to detect a relay attack at the individual-command level.

[[op_getLastExecutionResponse]]
===== Get Last Execution Response

[cols="1h,4", grid=rows, frame=all]
|===
| Signature   | `getLastExecutionResponse(idCommand: integer) -> byte array?`
| Since       | 2.0
| Description
| Returns the response of the command identified by `idCommand`. If several prepared commands share the same
  identifier, the response of the *last* matching command is returned.
| Parameters  | `idCommand` -- the application-supplied identifier of the command whose response is requested.
| Returns     | The response bytes, or `null` if no command with the supplied identifier produced a response.
| Throws      | None.
|===

===== Get Last Execution Responses

[cols="1h,4", grid=rows, frame=all]
|===
| Signature   | `getLastExecutionResponses() -> list<byte array>`
| Since       | 2.0
| Description
| Returns the responses collected during the last invocation of `processCommands()`, in the order in which the
  commands were prepared.

  This operation MUST NOT alter the internal state of the manager: the list of responses MUST remain available
  until `processCommands()` is invoked again, at which point it is replaced by the new set of responses.
| Returns     | A `list<byte array>` representing the command responses, in the order in which the commands were sent.
| Throws      | None.
|===

[[op_CardTransactionManager_prepareCommand_apdu]]
===== Prepare Command (APDU)

[cols="1h,4", grid=rows, frame=all]
|===
| Signature   | `prepareCommand(apdu: byte array) -> CardTransactionManager`
| Since       | 2.0
| Description | Prepares an APDU command without command identifier nor duration bound.
| Parameters  | `apdu` -- a non-empty `byte array` containing the raw APDU command.
| Returns     | The current instance (`CardTransactionManager`).
| Throws      | None.
|===

[[op_CardTransactionManager_prepareCommand_withId]]
===== Prepare Command (APDU, ID Command)

[cols="1h,4", grid=rows, frame=all]
|===
| Signature   | `prepareCommand(apdu: byte array, idCommand: integer) -> CardTransactionManager`
| Since       | 2.0
| Description
| Prepares an APDU command with an application-supplied identifier. The identifier MAY later be used to retrieve
  the corresponding response via <<op_getLastExecutionResponse,`getLastExecutionResponse`>>.
| Parameters
| `apdu`       -- a non-empty `byte array` containing the raw APDU command. +
  `idCommand`  -- the application-supplied identifier of this command.
| Returns     | The current instance (`CardTransactionManager`).
| Throws      | None.
|===

[[op_CardTransactionManager_prepareCommand_withDuration]]
===== Prepare Command (APDU, ID Command, Max Duration)

[cols="1h,4", grid=rows, frame=all]
|===
| Signature   | `prepareCommand(apdu: byte array, idCommand: integer, maxDuration: long) -> CardTransactionManager`
| Since       | 2.0
| Description
| Prepares an APDU command with an application-supplied identifier and a maximum tolerated exchange duration. The
  implementation MUST measure the effective duration of the corresponding APDU exchange and MUST raise an
  exception (the [CNA-TR-API] `InvalidCardResponseException`) if it exceeds the declared bound. The identifier
  of the offending command MUST be made available to the application through the exception message.
| Parameters
| `apdu`        -- a non-empty `byte array` containing the raw APDU command. +
  `idCommand`   -- the application-supplied identifier of this command. +
  `maxDuration` -- the maximum tolerated duration of the APDU exchange, in milliseconds.
| Returns     | The current instance (`CardTransactionManager`).
| Throws      | None at preparation time. The duration check is performed at processing time.
|===

[[type_GenericCardApiFactory]]
==== Generic Card API Factory

[cols="1h,4", grid=rows, frame=all]
|===
| Kind     | Interface
| Namespace  | `genericcard`
| Since    | 1.0
| Purpose  | Factory used by the application to obtain instances of the public types provided by the API.

The `GenericCardApiFactory` is the *only* normative entry point through which the application is allowed to
instantiate the public types of the API. Implementations MUST expose exactly one instance of this factory and MUST
guarantee that every invocation returns a fresh, fully initialised object.

[[op_GenericCardSelectionExtension_addSuccessfulStatusWord]]
===== Add Successful Status Word

[cols="1h,4", grid=rows, frame=all]
|===
| Signature   | `addSuccessfulStatusWord(statusWord: integer) -> GenericCardSelectionExtension`
| Since       | 1.0
| Description
| Adds a status word to the list of those that MUST be considered successful for the *Select Application* APDU.

  *Note:* the list initially contains the standard successful status word `9000h`.
| Parameters  | `statusWord` -- a positive `integer` lower than or equal to `FFFFh`.
| Returns     | The current instance (`GenericCardSelectionExtension`).
| Throws      | None.
|===

[[sec_behaviours]]
== Behavioural Requirements

. The list of successful status words declared on a `GenericCardSelectionExtension` MUST be cumulative: every call
  to `addSuccessfulStatusWord` adds to the existing set without removing the implicit `9000h` entry.
. `processCommands()` (inherited from [CNA-TR-API]) MUST execute the prepared APDUs in the order in which they
  were prepared; the resulting list returned by `getLastExecutionResponses` MUST preserve that order.
. When `prepareCommand(apdu, idCommand, maxDuration)` is used, the implementation MUST measure the effective
  duration of the APDU exchange and MUST raise an `InvalidCardResponseException` ([CNA-TR-API]) if the bound is
  exceeded; the message MUST identify the offending command by its `idCommand`.
. `getLastExecutionResponse(idCommand)` MUST be consistent with `getLastExecutionResponses()`: the byte array
  returned for a given `idCommand` MUST equal the corresponding element of the ordered list (when present).
